# openapi-operation

Status-exhaustive, runtime-validated JSON operations for TypeScript clients generated from OpenAPI.

`openapi-operation` connects three things:

- an [`openapi-typescript`](https://openapi-ts.dev/introduction) `paths` type;
- Zod request and response schemas generated from the same OpenAPI document;
- the platform `fetch` API.

An operation cannot compile when a documented status is missing, an undocumented status is added, or a schema disagrees with its OpenAPI type. At runtime, request inputs and the response selected by the actual HTTP status are parsed with Zod.

## Why this exists

Generated OpenAPI clients can expose a status-discriminated TypeScript union while still validating responses with a single success schema or a union of every error schema. That loses the runtime relationship between a status and its documented body: for example, a body belonging to `409` may be accepted for a `400`, and an undocumented status may be cast into the declared result union.

`openapi-operation` keeps that relationship intact. Each documented status must have its own compatible schema, the schema selected at runtime comes from the actual response status, and an undocumented status is rejected. The result is both status-discriminated at compile time and status-specific at runtime.

## Install

```sh
pnpm add openapi-operation zod
```

This package is ESM-only. It requires Zod 4 and a runtime with the standard `fetch`, `Request`, `Response`, `Headers`, and `URL` APIs. Node.js 22.18 or newer provides all of them; browsers do as well.

## Generate a contract

Given a FastAPI OpenAPI JSON document, the included generator produces the `openapi-typescript` contract, per-operation Zod schemas, and the exhaustive operation definitions together:

```sh
pnpm exec openapi-operation generate \
  --input ./openapi.json \
  --output ./src/generated/backend
```

The output directory contains:

```text
schema.ts
zod/
operations.ts
```

`operations.ts` exports a flat `operations` object keyed by the OpenAPI `operationId`. Every operation must have an `operationId`, and only numeric response statuses are supported.

Generated output can be committed and checked for drift in CI without rewriting it:

```sh
pnpm exec openapi-operation generate \
  --input ./openapi.json \
  --output ./src/generated/backend \
  --check
```

The generator intentionally uses `openapi-typescript` for static contract types and Orval only for Zod schema generation. Request execution and response dispatch remain owned by `openapi-operation` because the runtime schema must be selected using the actual HTTP status.

## Define operations manually

Assume `paths` was generated by `openapi-typescript` and the Zod schemas were generated from the same OpenAPI document:

```ts
import { createJsonOperationFactory } from "openapi-operation";
import { z } from "zod";

import type { paths } from "./generated/openapi.js";
import {
  UpdateProductBody,
  UpdateProductParams,
  UpdateProductQuery,
  UpdateProductResponse200,
  UpdateProductResponse400,
  UpdateProductResponse404,
} from "./generated/schemas.js";

const defineJsonOperation = createJsonOperationFactory<paths>();

export const updateProduct = defineJsonOperation({
  path: "/products/{product_id}",
  method: "patch",
  pathSchema: UpdateProductParams,
  querySchema: UpdateProductQuery,
  bodySchema: UpdateProductBody,
  responses: {
    200: UpdateProductResponse200,
    400: UpdateProductResponse400,
    404: UpdateProductResponse404,
  },
});
```

The `responses` object must contain exactly the numeric response statuses declared by the operation's OpenAPI type. If the backend adds a new documented response status or changes a response body, this definition stops compiling until the client handles the new contract.

## Call an operation

```ts
const result = await updateProduct(
  {
    baseUrl: "https://api.example.com",
    headers: { authorization: `Bearer ${token}` },
  },
  {
    path: { product_id: productId },
    query: { publish: true },
    body: { name: formData.name },
  },
);

switch (result.status) {
  case 200:
    showProduct(result.data);
    break;
  case 400:
    showValidationReason(result.error.data.code);
    break;
  case 404:
    showNotFound();
    break;
}
```

For a nested reason union, use the same ordinary TypeScript exhaustiveness pattern:

```ts
function assertNever(value: never): never {
  throw new Error(`Unhandled value: ${String(value)}`);
}

if (!result.ok && result.status === 400) {
  switch (result.error.data.code) {
    case "invalid_name":
      showInvalidName();
      break;
    case "name_taken":
      showNameTaken();
      break;
    default:
      assertNever(result.error.data.code);
  }
}
```

When the generated contract adds another reason, the `assertNever` call becomes a compile error until the new case is handled.

The returned union is discriminated by both `status` and `ok`:

- documented `2xx` statuses return `{ ok: true, status, data }`;
- documented non-`2xx` statuses return `{ ok: false, status, error: { status, data } }`.

Normal API errors are values, not exceptions. This keeps the status and its body linked during narrowing and makes exhaustive handling possible.

## Derive result types

Result utilities can derive the complete result union or select the result, response body, or error envelope for particular statuses:

```ts
import type {
  OperationErrorForStatus,
  OperationErrorOf,
  OperationResponseForStatus,
  OperationResultForStatus,
  OperationResultOf,
} from "openapi-operation";

type UpdateResult = OperationResultOf<typeof updateProduct>;
type Updated = OperationResultForStatus<typeof updateProduct, 200>;
type UpdatedProduct = OperationResponseForStatus<typeof updateProduct, 200>;
type UpdateError = OperationErrorOf<typeof updateProduct>;
type InvalidUpdate = OperationErrorForStatus<
  typeof updateProduct,
  400
>;
```

The status parameter can also be a union, such as `400 | 404`. TypeScript rejects statuses that the operation cannot return; `OperationErrorForStatus` additionally rejects successful statuses.

## Reject selected responses

An application can declare that selected response statuses reject the operation instead of reaching callers as result values:

```ts
const defineJsonOperation = createJsonOperationFactory<paths>()
  .withResponseRejectionHandlers({
    422: ({ data, method, path }) =>
      new BackendRequestValidationError(method, path, data),
  });
```

The handler receives the validated response data and returns the error that the operation throws. Configured statuses are removed from the returned result union, while their schemas remain required in every applicable operation definition. This lets the application define a global response policy without weakening contract validation.

## Request middleware

Request middleware transforms the completed `Request` immediately before the configured `fetch` function receives it:

```ts
const authentication = (token: string) => (request: Request) => {
  const headers = new Headers(request.headers);
  headers.set("authorization", `Bearer ${token}`);
  return new Request(request, { headers });
};

await updateProduct(
  {
    baseUrl: "https://api.example.com",
    requestMiddleware: [authentication(token)],
    fetch: customFetch,
  },
  input,
);
```

Middleware runs in array order. It can be asynchronous. Supplying middleware does not replace or wrap the custom `fetch` implementation.

Raw response middleware runs immediately after `fetch` and before response status lookup, JSON parsing, and Zod validation:

```ts
const authenticationFailure: ResponseMiddleware = async (
  response,
  request,
) => {
  if (request.headers.has("authorization") && response.status === 401) {
    throw new AuthenticationError(await response.clone().json());
  }

  return response;
};
```

Configure it per operation context with `responseMiddleware: [authenticationFailure]`. Unlike response rejection handlers, raw response middleware does not remove statuses from the result type because it may return or throw conditionally.

## Failure model

The operation throws when the client and server cannot safely honor the contract:

- `OperationInputValidationError` — path, query, or body input failed its Zod schema;
- `UndeclaredResponseStatusError` — the server returned a status absent from the OpenAPI operation;
- `MissingResponseBodyError` — a response expected to contain JSON was empty;
- `InvalidJsonResponseError` — the response was not valid JSON;
- `OperationResponseValidationError` — response JSON failed the schema for its status.

All package errors extend `OpenApiOperationError` and retain the operation method and path. Validation and JSON errors retain the original error as `cause`.

## Request behavior

- Path values are URL-encoded before replacing `{parameter}` placeholders.
- Query arrays are encoded as repeated keys, for example `?tag=featured&tag=sale`.
- `undefined` and `null` query values are omitted.
- Query objects nested below the first level are rejected. The package deliberately avoids guessing an OpenAPI serialization style.
- JSON bodies are serialized after Zod parsing.
- `Accept: application/json` is added by default. `Content-Type: application/json` is added only when a body is present. Caller-provided headers win.
- `204`, `205`, `304`, and `HEAD` responses are treated as bodyless and should use a schema such as `z.void()`.
- A custom `fetch` implementation can be supplied per call for tracing, retries, testing, or another transport policy.

Request objects are required when the OpenAPI operation declares that input location, even if every property inside the object is optional. Pass `query: {}` for an empty declared query. To make the entire input optional safely, make its schema accept `undefined`, for example `QuerySchema.default({})`; the runtime schema will still run and apply its default.

## What this package does not do

It generates OpenAPI types, Zod schemas, and a flat operation map, but does not generate application-specific client namespaces, React hooks, query integrations, mocks, or framework code. It provides extension points for request transformation and response rejection, but does not own authentication, retries, correlation IDs, telemetry, framework integration, or application-specific error policy. Those policies belong in the client package that exposes the generated operations.

It currently targets JSON operations with numeric response statuses. OpenAPI `default` responses, non-JSON media types, advanced query serialization styles, and streaming bodies are intentionally outside its scope.
